# 已实现的架构与取舍

```text
房主浏览器 ─ HTTPS / WSS ─ Worker API ─ SQLite Durable Objects
     │                       │          房间/邀请/字幕/短票据/限流
     │                       └─ 后端调用 Realtime API，保管长期密钥
     ├─ WebRTC P2P ───────────── 观看者（可直连，也可能经 TURN）
     └─ WebRTC ─ Realtime SFU ── 观看者（热备 / 回退 / 多人分发）

本地电影文件 → 独立源标签页 → 标签页采集视频与音频 → 上述媒体路径
             ↑ 外置 AAC M4A
             └─ 播放位置/暂停/倍速 → BroadcastChannel → 房间字幕时钟
```

## 控制面和媒体面分开

Worker 处理管理员、邀请验证、API 和静态资产；Room/Directory/AuthLimiter
Durable Objects 协调房间、目录、短票据和登录限流。源码中的内部 claims header
由 Worker 构造，并非可供任意公网客户端直接调用的独立开放服务。
聊天不持久化；房间、邀请、字幕及部分时钟/状态会存储，不能宣传“什么都不存”。

## 不是一遇到两人就只能 SFU

现有逻辑偏好小房间主持人扇出，最多三名 direct viewers，即房主+三名观看者。
它不是全员摄像头 Mesh：主要是主持人发送电影，多人直连会增加主持人的上传及编码负载。
是否直连取决于 NAT、ICE、UDP/TCP、代理、运营商及对端能力，不按省份或国籍决定。
TURN 转发可保留 P2P PeerConnection，但不是媒体不经服务器的直连。

当前 SFU 会话是起播与热备设计的一部分，代码不是“仅需信令、无需 SFU 凭据”的实现。
少量观众直连后仍可能收备用 SFU 流，增加上传/解码和出站成本。更多观看者可走 SFU，
但没有经过公开万人压力测试，“没有 UI 人数上限”不是无限容量的证据。

## 切路与重连

候选媒体先接入/预热，检查已解码画面，再进行 make-before-break；失败候选、代际过期
探测会被清理。控制通道短断保留媒体、参与者身份和重连宽限期。
观看端冻结 watchdog 与周期 P2P 重试可尝试恢复，但切路前检测通过并不能保证之后不冻结。
信令 Connected 也不表示视频一定可播放。状态栏须区分房主发布链路与观看端实际活动链路。

保留编码/码率/订阅参数作为已实现行为，不在本次开源过程中重新调参，以免把新优化当成
“长期稳定版本”。如果要改热备开销、无 SFU 模式或自建 Coturn/LiveKit，应另开功能测试。

## 本地播放器和字幕

浏览器选择本地文件创建 object URL，不经 HTTP 上传原片。电影仍会编码成实时媒体发给
观看者，所以“文件不上传”不等于“画面不离开电脑”。
源页通过 BroadcastChannel 报时间、暂停、缓冲、倍速；Capture Handle 校验选中源，
不可识别时显式确认；不要把另一个网站错误绑定到本地播放器。
中间起播请求最新时钟，连续时钟更新合并，服务器预算与发送频率协调。
字幕独立叠加在每个观看者页面，不烧进共享画面，各选语言。但不是 RTP 逐帧字幕嵌入，
真实接收缓冲/视频冻结与字幕时钟可能短时错位。

## 音频兼容路径

MKV 是容器，不能仅凭扩展名判断音频/视频是否支持。浏览器做有界元数据读取并提示
可能不兼容，不上传影片，也不把“未知”误报成“没有音频”。
本地工具调用用户的 FFmpeg 导出单条 AAC 立体声 M4A，网页 audio 元素跟随 video：
暂停、跳转、倍速、轻微漂移校正，音频缓冲时暂停画面；共享标签页音频时一起传出。
这不是通用 Host Companion/系统音频采集服务，也不会启动 localhost 后台服务或云端转码。

## 建议后续开源但尚未实现

可复现长时间基准、弱网测试矩阵、独立成本采样器、接收端字幕延迟校准、可选低开销
热备策略、Linux/macOS 原生工具、可选自建 TURN/SFU 适配器。它们不应出现在“已支持”列表。
云浏览器、DRM 播放、AI 实时翻译及 CDN 方案并非本仓库现有能力。
